# L-265 Schematic placement assist: place the ghost's block in its state

Kind: Research, then Ready (strong model)
Status: Vanilla trace read (2026-11-28); a faked-look experiment build is next

A mode in which using a block on a ghost cell places the schematic's block
there with the schematic's facing and states (maintainer 2026-10-26, while
deciding L-263; GitHub issue #85 asked for it).

## Decided
- It will be built (maintainer 2026-11-28, answering issue #85). Some
  servers forbid this kind of help, but so they do other Lamium features:
  following a server's rules is the player's part, as for the rest of the
  mod.
- Gameplay packets carry only what the player could send by hand, except
  the two exceptions below; any other change needs its own decision.
- Faked look (maintainer 2026-11-28): where a state follows the player's
  facing (stairs, furnaces, ...), the look sent for that one placement is
  the one that makes the schematic's state. Server-visible, this mode only.
- Target (maintainer 2026-11-28): the first ghost cell on the view ray,
  not only the cell vanilla would place into, sent as a click on a real
  neighbor's face. A ghost with no neighbor whose face (and click position)
  yields its state is not placed. A real block in front on the ray wins,
  as for the ghost pick.
- Held block (maintainer 2026-11-28): brought into the hand first with the
  ghost pick's step (L-263); nothing is placed when it is not carried.
- Switching (maintainer 2026-11-28): a toggle action (unbound by default),
  shown on the schematic HUD while on, and a settings row enabling the
  mode. Off, or with no ghost first on the ray, the use input is vanilla.
- Lifecycle: the faked look and any held placement last one placement;
  nothing is held across focus loss, world exit or dimension change
  (a LIFECYCLE.md line when built).

## Found in the SDK (26.60.4, headers only)
- `ItemUseInventoryTransaction`: action, block `mPos`, `mFace`,
  `mClickPos`, `mFromPos`, slot, item, `mTargetBlockId`; no rotation.
- `PlayerAuthInputPacketPayload`: `mRot`, `mYHeadRot`, `mInteractRotation`,
  `mCameraOrientation`, and an embedded `mItemUseTransaction`.
- Trace on 1.26.60 (VALIDATION-LOG "L-265 vanilla placement trace"): a
  placement is its own `InventoryTransactionPacket`, and the local server
  places with the rotation of the auth input sent just before it (`mRot`),
  not the client's newer one. So the faked look goes into that auth input
  and the placement waits one tick (as Sneak placement's hold). Client and
  server placed the same states: stairs facing from yaw and upside down
  from the click height, slabs' half from the click height, logs' axis
  from the face.
- State comes from the virtual `BlockType::getPlacementBlock(by, pos,
  face, clickPos, itemValue)` (MCAPI; 44 block classes override it).
  Candidate solver: try the neighbor faces, click heights and looks,
  calling it with the local player's rotation set for the call, and keep
  the first combination that yields the ghost's state. Unverified:
  data-driven blocks (trait placement) may not go through it.
- Vanilla's build calls run only on a block hit; a ghost with air behind
  needs the assist's own trigger, queued to the tick (rule 2).
- `useItemOn`/`buildBlock` are already hooked by CameraInteraction,
  EdgeGuard and Sneak placement; their order with the assist is to decide.

## Open
- Experiment questions: whether a faked `mRot` (with `mYHeadRot` and
  `mInteractRotation` matched) for one tick is accepted and placed with,
  with no correction while walking; whether the server accepts a click on
  a face the ray never hit (reach from `mFromPos`) and what it resends
  when refused.
- Maintainer: whether holding use keeps placing ghost after ghost.
