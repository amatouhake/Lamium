# L-265 Schematic placement assist: place the ghost's block in its state

Kind: Research, then Ready (strong model)
Status: Scope agreed (2026-11-28); the state research is next

A mode in which using a block on a ghost cell places the schematic's block
there with the schematic's facing and states (maintainer 2026-10-26, while
deciding L-263; GitHub issue #85 asked for it).

## Decided
- It will be built (maintainer 2026-11-28, answering issue #85). Some
  servers forbid this kind of help, but so they do other Lamium features:
  following a server's rules is the player's part, as for the rest of the
  mod.
- States (maintainer 2026-11-28): the placement Lamium sends carries what
  makes the schematic's state, whatever the player is looking at: the
  clicked face and click position, and where the state comes from the
  player's facing (stairs, furnaces, ...), a faked look sent for that one
  placement. This is a server-visible trick, accepted for this mode only.
- Target (maintainer 2026-11-28): the first ghost cell on the view ray,
  not only the cell vanilla would place into. Lamium sends the placement as
  a click on a real neighbor's face that puts the block there; a ghost with
  no real neighbor to click cannot be placed. A real block in front of the
  ghost on the ray still wins (as for the ghost pick).
- Held block (maintainer 2026-11-28): when the hand does not hold the
  ghost's block, it is brought into the hand first with the ghost pick's
  step (L-263: hotbar slot, else from the inventory; in creative given when
  the creative inventory lists it); when it is not carried nothing is
  placed.
- Switching (maintainer 2026-11-28): a toggle action (unbound by default),
  shown on the schematic HUD while on, and a settings row that enables the
  mode. The use input stays vanilla while it is off or when the ray meets
  no ghost first.

## Open (research)
- How a placement reaches the server on 1.26.60: the item-use transaction's
  fields (block position, face, click position, player position, held
  item, target block) and where the server reads the facing from (the
  transaction, the last `PlayerAuthInputPacket` rotation, or the actor).
  What a faked look must change so the server places the state, and how
  the client's own prediction is kept from placing something else.
- Per block family, which inputs make which state: facing (horizontal,
  six-way, opposite of look), half/top from the click position, axis from
  the face, slab type, doors and beds (two cells), attachments (torches,
  buttons on a face). States no placement can produce (e.g. a stair's
  shape, connections) are left to the game.
- Confirmation from the placed block (authoritative state) and what is
  shown when the server placed something else.
