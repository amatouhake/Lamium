# L-71 Start an elytra glide from the mod

Kind: Research (cheap models may collect traces), low priority
Status: Open; headers read 2026-11-12, next trace not run

After L-70 puts an elytra on in mid-air, start the glide without a second
jump press. Split from L-70 (2026-09-30).

## Decided
- No faked flags or packets: only a vanilla path that the server accepts.

## Open
- Hypothesis (not confirmed): the jump key in mid-air sets the glide intent
  on the input request, the intent system checks the worn elytra and the
  fall state, and the action system sets the flag and queues the auth input
  action. `tryStartGliding` called outside that order would then fail or
  have no packet behind it, which matches the L-70 traces.
- For the maintainer: whether setting `mHasGlideIntent` for one tick after
  a confirmed swap counts as "a vanilla path" (it is what a jump press does,
  if the hypothesis holds) or as a faked flag. Not decided.

## Next
Trace, read only: log `mHasGlideIntent`, `isGliding()`,
`MobGliding::getFallFlyTicks` and the worn chest item on each client tick
around a vanilla jump-to-glide, and around an L-70 swap followed by the
player's own jump press. That shows on which tick after the swap vanilla
itself accepts a glide.

What the SDK 26.60.4 headers show (read only, nothing run):
- Gliding starts through entity systems, not a `Player` call:
  `PlayerInputRequestComponent::mHasGlideIntent` (next to `mHasFlyIntent`),
  `StartGlidingIntentSystem`, `StartGlidingActionSystem::createSystem(isClientSide)`
  (opaque), `GlideInputSystem::doGlideInputSystem` (abilities, move input,
  actor data flags, `FallFlyTicksComponent`, the state vector).
- Packet side: `PlayerAuthInputPacketPayload` action `StartGliding = 32`
  (and `PlayerActionType::StartGliding = 15`). `Player::startGliding`,
  `stopGliding` and `tryStartGliding` are `MCAPI`.

## Tried
- `Player::tryStartGliding` on the swap tick and the next three ticks:
  always false (traces at 5728561 and 05648bf). Without a worn elytra
  vanilla never calls it.
