# L-353 Input events and the client thread: what is still touched outside the tick

Kind: Research
Status: Open, not started; nothing here is known to misbehave

Rule 2 (AGENTS.md) says key and mouse events arrive outside the client tick
and no game pointer is kept across frames. The 2026-11-16 pre-release review
found two places that do not follow its wording and were left as they are.

## Known
- `IClientInstance*` is kept across frames and read inside input listeners
  (`getScreenName()`, `getTopScene()`, `getLocalPlayer()`):
  `SchematicActions.cpp` (the wheel listener), `CameraSessions.h` /
  `CameraSessions.cpp`, `SettingsScreen.cpp` (`client`) and
  `CustomInput.cpp` `process`, which asks `ll::service::getClientInstance()`
  on each event. Reads only; the object lives as long as the process.
- `interaction::periodic::stop()` (`PeriodicInput.cpp`, from
  `Runtime::disable`) calls the game's button callbacks directly. A comment
  in `FakeOffhand.cpp` ("Never touch input handlers off the client thread")
  suggests a shutdown disable can run off the client thread.
  `interrupt()` itself is deferred to the next input update since
  `c4602457`.
- `scroll_drag::release()` now also runs from the `onAppFocusLost` hook
  (`cancelInputCapture`), on the same unproven thread assumption as the
  `finishNumber()` call that was already there.

## Open
- Which thread `KeyInputEvent` / `MouseInputEvent`, `onAppFocusLost` and
  `Runtime::disable` run on. One log line with the thread id in each, on
  the Dev instance, answers it.
- If they are the client thread: say so in rule 2 and in `CustomInput.cpp`'s
  comment, and close this item with no code change.
- If not: whether the listeners' reads move behind the queue (screen name
  and player presence captured on the tick), and `stop()` defers like
  `interrupt()`.

## Next
The thread-id log, then the choice above with the maintainer.
