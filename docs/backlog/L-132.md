# L-132 Move while the inventory screen is open

Kind: Research, then Feature
Status: Parked 2026-10-10 after eight trial rounds without smooth movement; resume from Next

While the player's own inventory screen is open, keep walking, jumping and
sprinting from the bound movement keys, so items and armor can be arranged
on the move. The camera cannot turn (the mouse belongs to the screen).
Requested by the maintainer 2026-10-10.

## Decided
Direction agreed 2026-10-10:
- Only the player inventory screen at first; containers and other block
  screens later, if at all.
- Sneak is not passed through: Shift is shift-click (quick move).
- Paused while a text field has focus (creative search, recipe book search)
  and on focus loss.
- Default off; the help text warns that some servers may treat moving with
  an open inventory as cheating (like Auto Attack's warning).
- No game state touched from the window procedure (AGENTS.md rule 2).

## Next
Find where `mMove` is zeroed while a non-play screen is on top (inside
`ClientInputUpdateSystemInternal::tickUpdateClientInputView`, perhaps via
`VanillaClientGameplayComponent` or a play-screen check), or whether the
input handler routes movement button events to `ClientMoveInputHandler`
only while the gameplay mapping is active
(`ClientInputMappingFactory::_activateMapping`).

## Tried
Trace build `xmake f --inventorymove_trace=y`
(`src/features/interaction/InventoryMoveTrace.cpp`), single player on
1.26.51.01, commits 7e56cc8..40de3e3:
- Facts: `ClientInputUpdateSystem::extractRawHIDInput` keeps running
  (~20/s) with `inventory_screen` open; vanilla's bindings read from
  `getOptions().getCurrentKeyboardRemapping()` (`key.forward` = 87, ...,
  `key.sprint` = 17). Bedrock's move x is positive to the left.
- Raw flags written after extraction: gone again by
  `PlayerMovement::calculateMoveVector` (two calls per tick: the
  `RawMoveInputComponent` state and a second, likely the local server's).
- Flags written into `MoveInputComponent`'s states after
  `inputHandlerUpdatePlayerState` (vector forced): reach
  `calculateMoveVector`, but `MoveInputComponent::mMove` and the
  `PlayerAuthInputPacket` stay zero; the player moved only by server
  corrections (~2/s, jerky), no jump, and kept walking after the screen
  closed. Patching the auth packet's move vector and flags did not help.
- Not the cause: `MoveInputComponent::Flag::MoveInputStateLocked` and the
  client input locks are clear; forcing `UIScene::absorbsInput` false for
  the inventory changes nothing; copying the gameplay bindings
  (`button.up/down/left/right/jump/sprint` from `gamePlayNormal`) into the
  `screen*` input mappings changes nothing.
