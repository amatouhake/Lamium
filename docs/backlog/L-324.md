# L-324 Map: custom blocks are drawn in a dirt-like brown

Kind: Ready (strong model; cause unconfirmed, fix rule agreed)
Status: Built (first clause of the rule), not checked in game

On the minimap and world map, add-on blocks show brown instead of their own
color, while the game's map item shows the color of their
`minecraft:map_color` component (issue #76, reported on 0.6.0, game 26.60,
with steps: an add-on with such blocks, a filled area, compare with a map
item).

## Decided
- How Lamium colors a block today (`Minimap.cpp`, `blockLook` /
  `blockColor`): the average of the top texture from `BlockGraphics`, times
  the biome tint; the game's `getMapColor` only when no texture color was
  found.
- Fix (maintainer 2026-11-15): a block outside the `minecraft` namespace
  that defines `minecraft:map_color` is drawn in that color. Other blocks
  keep the texture color; a texture that is the default/missing one falls
  back to `getMapColor`.
- Hypothesis behind the brown, not checked: for add-on blocks
  `BlockGraphics` hands back a default texture.

## Built
- `blockLook`: a block outside `minecraft:` whose state has a
  `BlockMapColorComponent` (`Block::tryGetComponent`, links on 26.60.4) with
  a visible color takes that color, cached per state like the texture, with
  the component's `mTintMethod` as tint (agent's choice: it is the tint the
  add-on gave its map color). Rule in `MapColors.h` (`usesDefinedMapColor`),
  tested. Read under the capability "Map colors of add-on blocks", failing
  open to the texture color.
- The diagnostics log names the first 8 add-on blocks: component yes/no,
  color, top texture path, which tests the brown hypothesis.
- Saved map tiles keep the colors they were recorded with: an area shows the
  new color once it is scanned again (visited); `columnRevision` was not
  raised, so nothing is re-recorded wholesale.

## Known/Tried
- The default/missing texture clause is not built: the SDK has no way to
  recognise it. `MissingTextureAtlasItem::missingTextureItem()` is `MCNAPI`
  and does not link (tried 2026-11-15); `TextureUVCoordinateSet` carries no
  missing flag; `BlockGraphics::getDefaultTextureName` is `MCNAPI`. A
  texture image that cannot be read already falls back to `getMapColor`.
- Not known from the headers: whether the game gives every add-on block a
  default map color component. If the log shows `map_color yes` for blocks
  the add-on did not give one, the component alone does not mean "defined".
