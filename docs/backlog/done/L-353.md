# L-353 Input events and the client thread: what is still touched outside the tick

Kind: Research
Status: Done 2026-11-26; one thread seen in game on `52babf18`, rule 2 rewritten

Rule 2 (AGENTS.md) said key and mouse events arrive outside the client tick
and no game pointer is kept across frames, while five places kept the
client instance and three input listeners read through it. L-405 Client
pointers kept across frames was merged into this item.

## Decided (maintainer 2026-11-26)
- The `thread_trace` build logged UI render, key and mouse events, the
  client tick, focus loss, world exit and `Runtime::disable` at quit on one
  thread (VALIDATION-LOG.md, 2026-11-26). So reading the client inside
  those listeners is safe; changing game state there still goes through
  the queue, because it runs between ticks.
- Rule 2 names the client instance as the one game pointer a feature may
  keep while it runs, cleared when it stops (it outlives a world). The
  schematic adjust key's `adjustClient` is now cleared in `stopAdjust()`;
  the others already were (camera, world map and settings screen on close
  or exit, Periodic input with its owners).
- No script flags stored game pointers (too many false hits).
- The trace left with this item (L-403's policy); git has it at `52babf18`.

## Known
- The SDK does not show how long the client instance lives: `MinecraftGame`
  keeps them as `shared_ptr` by sub-client id. `ClientExitLevelEvent` hands
  it over and the settings screen works with no world.
- `FakeOffhand.cpp` still checks the thread before touching input handlers
  in a disable; harmless, kept.
