# L-324 Map: custom blocks are drawn in a dirt-like brown

Kind: Ready (strong model)
Status: Done 2026-11-15 on `2cc9db54` (seen in game on `f164c145`), confirmed by the maintainer

On the minimap and world map, add-on blocks showed brown instead of their
own color (issue #76, reported on 0.6.0, game 26.60).

## Decided (maintainer 2026-11-15)
- Every block, vanilla or add-on, is drawn as it looks: its top texture's
  average. `getMapColor` only when Lamium finds no look: `BlockGraphics`
  gives `textures/blocks/missing_tile`, or the image cannot be read. A
  texture name the atlas does not know draws the game's magenta-and-black
  checker, and the map shows its purple, whatever the map color.
- An add-on block's texture comes from its `minecraft:material_instances`
  ("up", else "*") when `BlockGraphics` has none. The earlier "add-on map
  color first" rule was dropped.
- The run-time type id lookup below stays, behind its capability, until the
  SDK links the component (listed in L-315).

## Built
- `blockLook` / `topMaterial` (`Minimap.cpp`), rule in `MapColors.h`
  (`knownTexture`, `topFaceRank`, `lookSource`), tested; cached per state.
- `Block::tryGetComponent<BlockMaterialInstancesComponent>` does not link:
  the game's `type_id<void, BlockMaterialInstancesComponent>` static is
  resolved by name with `SymbolView`, then `_findComponentBase` on the
  state, else the type. Gated by the capability "Map colors of add-on
  blocks (block material instances)"; off, such blocks take the map color.
- The diagnostics log names the first 8 add-on blocks with the path used.
- Saved tiles keep their colors until scanned again.
- Test packs: `tests/packs/map-color` (generator in `tools/`), four blocks
  that tell the paths apart; installed on the Dev instance.

## Seen
- 2026-11-15 on `f164c145`: A cyan, B yellow, C and D the checker's purple,
  each as it looks in the world. The first packs (without
  `minecraft:geometry`) loaded no textures.
