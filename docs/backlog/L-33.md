# L-33 Mob growth and breeding timers in the target card

Kind: Research
Status: Probe done 2026-11-12; waiting for the maintainer: states only, or read the local server

The maintainer wants the time until a baby mob grows up and the remaining
breeding cooldown in the target card (asked 2026-09-24; not part of L-08).

## Decided
- The client actor has neither `AgeableComponent` nor `BreedableComponent`
  (probe 2026-11-12, `world_probe` build, a baby cow and a baby squid in a
  local world: `baby=true`, no component). It only receives the synced
  `Baby` and `Inlove` flags.
- Estimating from observed events (feeding speeds growth up) is not
  accurate enough to show as a time.

## Open
For the maintainer: a timer needs the local server's actor (singleplayer
only), or the card shows only "baby" / "in love" and says so in the help
text. Recommended: the states only; the server read is a large new
dependency for a number most players check rarely.

If the server read is chosen, what is known (SDK 26.60.4 headers):
- `AgeableComponent::mAge`; `BreedableComponent::mLoveTimer`,
  `mBreedCooldown`, `mBreedCooldownTime`, `mLoveCause`.
- `IClientInstance::getServerData()` (virtual) returns the in-process
  `Minecraft`; `MinecraftGame::getServerInstance()` exists;
  `Actor::getOrCreateUniqueID()` links (`MCAPI`) and keys the same actor
  there. Not known: whether `tryGetComponent` links for the two types.
- The server level ticks on its own thread, so reading its actors from the
  client thread is a data race unless the read is queued onto the server
  thread and plain values copied back. Lamium touches the local server
  nowhere today; this would be a new kind of game dependency.
