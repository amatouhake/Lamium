# L-299 Screenless inventory moves can leave a slot stuck when client and server desync

Kind: Research.
Status: Open; question 1 read in code (`8cdfe543`, 2026-11-12), waiting for a reproduction. No release target.

A slot can behave as locked after a client/server desync. A Discord report
(2026-10-31) blamed Hand Restock after placing a lava bucket; the maintainer
could not reproduce it (single-player, BDS 1.26.51) and closed it on
2026-11-01 as not reproducible. The class of problem is real anyway: a
desync predates client mods (fast vanilla play, item pickup and consumption;
a local world also runs an integrated server), and the maintainer hit the
same lock while building the shared screenless-move layer (`game::beginTransfer`,
`movePair`) used by Hand Restock, Transfer, Sort and the equipment swaps;
leaving and rejoining the world cleared it. The reporter's log had the shared
layer's "Inventory transfer stopped: response 2" (`TransferSession.cpp`,
result not Accepted), not a Hand Restock line.

## Decided
- No fix work from the original report: it does not meet the 2026-11-01
  reopening condition (exact steps anyone can reproduce with public
  releases, plus that session's log and a short video).
- Direction (maintainer 2026-11-02): suppressing occurrence is not the
  promising line; Lamium's moves can at most avoid adding to it. The product
  is repair after the fact: re-trigger the desync, find which state is
  stale, catalogue recovery steps from lightest to heaviest. A safe
  in-session resync may ship as a recovery feature. It may only restore
  from authoritative server state, never synthesize, rewrite or forge items,
  and must fail open to vanilla.
- Existing rules this builds on: a Hand Restock move waits for a server
  update showing the consumption (HAND-RESTOCK.md "Ordering the move",
  `a41f0f2`); bulk moves wait for all responses and stop and drop the queue
  on a rejected, timed-out or unexpected result (DESIGN, L-169).

## Open
1. Can Lamium state (pending operation, transfer token, predicted snapshot)
   outlive a failure? Code read says no: `RequestTracker.cpp` has one owner,
   released only by `cancelTransfer`, and every owner (Hand Restock, Sort and
   the screen transfer session via `ScreenTracker`, Repeat trades) releases
   it on every failure path read; a missing response ends as `TimedOut` after
   5 s. A leaked token would make Lamium's own moves refuse
   ("begin-token-unavailable"), not lock a vanilla slot. Not run.
   Two unconfirmed client-only sources in `game::movePair` / `giveCreative`
   (`InventoryMove.cpp`):
   - both slots are set through the client's setters first; with no
     transaction pending afterwards it logs "recorded-nothing-pending"
     (trace builds) and still returns true. Whether anything was sent then
     is unknown.
   - Tool guard, Elytra swap, Bring to hand, Death restore, Offhand swap,
     Tool switch and Weapon switch send with no response tracking; a
     rejected legacy transaction relies on vanilla's correction.
2. Does vanilla alone leave the same stuck slot under fast repeated
   use/pickup/consumption? For learning the residue's shape, not blame.
3. Which recovery clears it, and the lightest reliable one? Relog works, so
   the authoritative state was intact. Test reopening the inventory,
   interacting with the slot, changing dimension.
4. Can a stuck slot be detected client-side, and can the client get a fresh
   authoritative inventory snapshot without leaving the world? Decides
   whether a recovery feature is feasible, and automatic or manual.

## Next
Starts from the maintainer's deliberate re-triggering, a public
reproduction, or a session log pairing "Inventory transfer stopped" with the
stuck slot's state. Use a `restock_trace` build (logs every `Move:` stage;
no new hook needed) to see whether "recorded-nothing-pending" or a rejected
response precedes the stuck slot. Record: the slot's contents before and
after each recovery step; whether a Lamium operation owns the tracker then;
the same fast-use sequence with each screenless-move feature on and off;
local world and BDS.
