# L-169 Item Transfer: remaining gesture and screen extensions

Kind: Design
Status: Waiting for the maintainer to choose any extension; none approved

Item Transfer's core gestures shipped (matching/everything, keep-one and
native slot-role routing in 0.2.2; held-stack matching and the four drop
gestures in 0.2.3). This item holds the extensions not chosen. L-154 is
merged here.

## Decided
- All five held-stack/drop switches default on (maintainer).
- Current behavior and confirmation rules: DESIGN.md "Inventory transfer"
  and [ITEM-TRANSFER.md](../ITEM-TRANSFER.md). Do not implement the old
  proposal/handoff kept in BACKLOG-DONE.md again.

## Open
- Extra Shift + double-click (matching) or Ctrl + Shift + click (leave one)
  bindings: do they add value beside the shipped gestures?
- "Fill existing stacks only" and W/S-directed moves (the latter explicitly
  deferred, not selected).
- Additional screen families: reproduce a specific unsupported operation
  and confirm its native slot roles before extending coverage.

## Known (read 2026-11-17)
- `TransferGesture.h` `dragGesture`: Ctrl wins, so Ctrl + Shift + left is
  already One drag; a "leave one" click would change that precedence
  (Shift + right drag already leaves one).
- No double-click timing exists; Shift + left's first press already moves
  a stack, and Alt + click already moves matching items.
- "Fill existing stacks only" cannot use the game's auto-place; it needs
  per-slot placement (`chooseDestination`, used in the inventory screen
  only) in every screen.
- Screens are covered generically (`TransferRoutes.cpp` `supported()`);
  a failing screen has to be reproduced first (`transfer_trace`).

## Next
Nothing until the maintainer picks an extension. The full gesture/screen
matrix, drop-key rebinding, controlled rejection or timeout, lifecycle
interruption, unverified-game fallback, packs and wider server checks are
validation gaps, not unfinished gestures: see Pre-release checks and
VALIDATION.md.
