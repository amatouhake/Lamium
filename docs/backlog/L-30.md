# L-30 Ender Dragon multipart hitboxes on Bedrock

Kind: Research
Status: Probed: parts are readable on the client; waiting for a real End dragon check, a server check and the color choice

The hitbox overlay should tell the dragon's damageable parts apart (at least
head vs the rest, ideally all eight) instead of drawing only its coarse
actor AABB.

## Decided
- Use the client's actual damage/targeting boxes. Do not derive boxes from
  render bones or copy Java dimensions.
- `EnderDragon` has eight `AABB*` members: `mHead`, `mNeck`, `mBody`,
  `mTail1`..`mTail3`, `mWing1`, `mWing2` (`_hurt(AABB* part, ...)` takes the
  hit part). Probe 2026-11-12 (`world_probe`, VALIDATION-LOG): on a dragon
  summoned in a local Overworld all eight are non-null on the client and
  point to world-space boxes that move with it (head 1x1x1, neck 3x3x3, body
  5x3x5, tails 2x2x2, wings 4x3x4). No symbol request needed.
- Reading the members depends on the class layout, so that path asks
  `versionSensitiveAllowed`.
- If the parts prove unusable, record the limit and leave L-11's ordinary
  entity hitboxes unchanged.

## Open
- Colors and labels (maintainer). Recommended: the existing hitbox color for
  the parts and the existing highlight color for the head (`mHead`), no new
  palette entry.

## Next
- Check on a real Ender Dragon in the End (summoned/custom entities are not
  enough evidence) and on a server, then build: feed the eight boxes to the
  normal hitbox overlay (today it reads only `Actor::getAABB()`,
  `WorldOverlay.cpp`).
- Fallback data if needed: `SubBBsComponent::mSubBBs` and
  `HitboxComponent::mHitboxes` via `tryGetComponent`; check that it links
  first (`Block::tryGetComponent<BlockInstrumentComponent>` did not in
  L-305).
