# L-165 Mass Craft: craft a recipe many times at once

Kind: Design, then Research (strong model).
Status: Open; priority raised 2026-11-17 without a place in the execution order; needs the purpose-and-scope conversation a larger feature starts with. No release.

Turn a whole inventory of ingredients into products with one action (logs
into planks, iron into blocks), instead of repeating fill-the-grid and
take-the-output by hand.

## Decided
- Ctrl + click on a recipe in the recipe book crafts all, no count in the
  first version, default off: Ctrl + click lies close to Shift + click and an
  accidental mass craft would hurt (maintainer 2026-10-12).
- Crafting from nearby chests is out.
- Priority raised, but no place in the execution order (maintainer
  2026-11-17).
- Designed as part of the recipe viewer ([RECIPES.md](../RECIPES.md),
  maintainer 2026-11-18): a craft is started from a recipe shown there, not
  from a separate list of stored recipes, and the research into placing a
  recipe in the grid covers it. Whether Ctrl + click in the game's own
  recipe book stays beside that is open.

## Known
Read with the `craft_trace` build in a local world (VALIDATION-LOG
2026-11-18):
- A click on a recipe in the game's book fills the grid with as much as
  divides evenly (64 logs into one cell; 60 of 64 ingots over six cells),
  one ordinary place request per cell, and sets the manager's selected
  recipe.
- Taking the output by a plain click is one craft request (`CraftRecipe`,
  one craft). One request can carry many: `CraftRecipeAuto` was seen with
  16 crafts (64 logs' planks: a stack of output) and with 7 (iron blocks
  from 64 ingots, straight from the inventory with an empty grid). Which
  press sends it is not settled: the screen's own calls for it are not
  among those Lamium can hook.
- The SDK does not provide the screen's and the manager's "recipe
  selected" and "craft all" calls (`_handleRecipeSelect`,
  `handleRecipeSelect`, `autoCraftItem`) nor the client's request
  constructor. It does provide the slot calls Item transfer uses
  (`_handleAutoPlace`, `_handleTakeAmount`, `$_handleTakePlace`,
  `$_handlePlaceOne`) and `_evacuateCraftingGrid`.

## Open
- Whether a "craft the last recipe again" key is wanted (agent: not in the
  first version).
- Agent's proposal for the rest (not decided):
  - Lamium lays the ingredients into the grid with the slot calls it
    already uses for Item transfer, then takes the output with the game's
    own Shift take, round by round, until the ingredients run out, the
    output would not fit or the player stops. Lamium never builds crafting
    requests; the server validates every round.
  - One round at a time: the next starts only after authoritative state shows
    ingredients down and output up; a mismatch or timeout stops with a toast.
    A per-tick bound keeps the rate modest.
  - Stops on screen close, any player click or key, focus loss, world or
    dimension change. Never drops items: check room before each round.
  - The 2x2 inventory grid and the crafting table first; stonecutter, loom,
    smithing and furnaces later or out.
  - A progress toast ("Crafting 320/640") and the total at the end.
- Watch out for: leftovers (buckets, bottles), recipes accepting several
  ingredient kinds (any log), the OreUI recipe book versus the JSON UI screen
  (L-130 found only the latter covered), servers limiting request rates
  (help-text warning like Auto Attack's).

## Next
A second trace build that lays one recipe into the grid with the slot
calls and takes the output with Shift, in a local world and on a server:
how many crafts one take makes, and what happens when the output does not
fit. Before that, the maintainer says which presses sent the two
`CraftRecipeAuto` requests.
