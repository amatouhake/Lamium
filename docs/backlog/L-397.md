# L-397 Lay recipes in with the game's own recipe-book request

Kind: Research
Status: Open; the calls do not link (2026-11-23), a trace looks them up by name at run time

Lamium lays a recipe into the crafting grid one cell at a time through
the slot calls (`RecipePlace.cpp`: a move straight from a slot, else by
the pointer), waiting for the grid to empty first. The game's recipe
book lays a whole recipe in with one request and never goes by the
pointer. If Lamium could send that request, placing would be one step,
and the waiting and per-cell paths could go (maintainer 2026-11-23).

## Decided (maintainer 2026-11-23)
- Placing a recipe and Mass Craft stay apart (L-388): Mass Craft's
  request count, free slots and throws are its own to tune; this item is
  about placing. Whether Mass Craft uses the request too is looked at once
  it is known to work.

## Known (2026-11-23)
- The recipe book's path: `CraftingScreenController::_handleRecipeSelect`
  (collection, index, displayOnly), the manager's `handleRecipeSelect`
  (the same and the auto-place list) and `autoCraftItem` (a recipe cell,
  `ItemCraftType` All or One, the list). A cell names the recipe; the
  manager keeps the book's list in `mRecipes`, and `Recipe::mRecipeNetId`
  is readable (the craft trace prints it).
- `ItemStackRequestActionCraftRecipeAuto` (action 13): a `RecipeNetId`, a
  craft count and the ingredients. Which click sends it (the lay-in, or a
  Shift click that crafted with the grid empty, L-165) is not known.
- None of the four links on SDK 26.60.4 (linked 2026-11-23); v26.60.9's
  headers still mark them `MCNAPI`, so a newer SDK does not help. Mangled:
  `?autoCraftItem@CraftingContainerManagerController@@QEAA_NAEBUSlotData@@W4ItemCraftType@@AEBV?$vector@UAutoPlaceItem@@V?$allocator@UAutoPlaceItem@@@std@@@std@@@Z`,

  `?_handleRecipeSelect@CraftingScreenController@@QEAAXAEBV?$basic_string@DU?$char_traits@D@std@@V?$allocator@D@2@@std@@H_N@Z`,

- Lamium already resolves one game symbol by name at run time

## Tried
- L-165 (2026-11-19): the virtual "slot pressed" and `_handleAutoPlace` on
  a recipe cell did nothing.

## Open
- Whether the calls resolve by name at run time and, replayed from
  Lamium with the pointer elsewhere, lay a recipe in; whether a cell can be
  named for any recipe (book closed, another tab, filtered, locked).
- Whether a server takes it for a recipe the player has not unlocked in
  the book, and with what the grid already holds.
- The recipe's net id from Lamium's table, and how many crafts one request
  lays (a stack a cell, as Shift does in the book).
- What the client shows meanwhile: the grid filled at once or after the
  server's answer; a refusal's look.
- The furnaces, the stonecutter and the smithing table, which have
  requests of their own or none.

## Next

real click with their arguments, replay the last one from a key, log
`mRecipes` against the hovered cell. Then the maintainer decides whether
a shipped feature may rest on names found at run time, or whether these
join L-315's symbol request.
